# ウエポンマスター 技術要件定義書

## 1. 技術選定の前提

開発言語はPHPを軸とする方針のため、一般的なゲームエンジン(Unity/Godot等)ではなく、
**PHP(Laravel)ベースで、Webとデスクトップ両方に展開できる構成**を採用する。

**リリース方針: Web先行 → 後日デスクトップ化(段階的リリース)**
- **第一段階**: Webサイト(ブラウザ)として公開し、コアロジック(配置・合成判定・
  ランク計算・非同期PvP)を作り込み、実際に遊んでもらいながら検証する
- **第二段階**: 同じLaravelコードベースを**NativePHP**でラップし、
  Windows/Mac/Linux向けデスクトップアプリ化する(Steam配布などはこの段階以降で検討)
- Web版・デスクトップ版は**同一のPHP/Laravelコードベースを共有**することを前提に設計する

**採用方針: PHP(Laravel)+ NativePHP構成**
- PHP(Laravel)でゲームロジック・データ管理を記述(Web版・デスクトップ版で共通)
- Web版はLaravelを通常のWebアプリとしてホスティングして提供
- デスクトップ版はNativePHPによりElectronベースのアプリとしてパッケージング
- 画面描画はHTML5 Canvas + JavaScriptを使用(ブラウザ技術がベースのため描画部分は不可避。
  Web版・デスクトップ版どちらでもそのまま動作する)
- ゲームルール・状態管理・データ永続化のロジックは全てPHP側に集約する

**設計方針**: 「ロジックはPHP、描画のみJS」という役割分担を徹底し、
JS側はCanvas描画とPHP側APIの呼び出しに専念する薄いレイヤーとする。
この役割分担を徹底しておくことで、後日のデスクトップ化(NativePHPでのラップ)を
コード変更なしでスムーズに行えるようにする。

## 2. アーキテクチャ概要

```
[第一段階: Webアプリ]              [第二段階: デスクトップアプリ(NativePHP/Electron)]
   同じLaravelコードベースを               同じLaravelコードベースを
   通常のWebホスティングで提供    →       NativePHPでラップして配布

   ├─ フロントエンド層(HTML5 Canvas + JS)  ※Web版・デスクトップ版で共通
   │    - グリッド配置のUI描画
   │    - 戦闘アニメーション再生
   │    - PHP側APIへのリクエスト送信のみ担当(ロジックは持たない)
   │
   └─ バックエンド層(PHP / Laravel)          ※Web版・デスクトップ版で共通
        - 武器・素材・レシピのマスタデータ管理
        - 配置バリデーション(グリッド衝突判定・シナジー計算)
        - 戦闘シミュレーション処理(ATK/SPD計算、勝敗判定)
        - ランクポイント・階級判定処理
        - セーブデータ・非同期PvP用データの永続化
```

- Web版はDBを共有サーバー(例: MySQL)で運用
- デスクトップ版はNativePHP標準のSQLiteをローカル保存に利用しつつ、
  ランクマッチ・非同期PvPなど**サーバーが必要な機能は同一のAPIサーバーに接続**する

## 3. データ構造(初期設計)

検証用仕様書(武器5種・素材3種・レシピ4種)に対応するデータモデル。

### 3.1 武器マスタ(weapons テーブル想定)
- id
- name(武器名)
- grid_width / grid_height(占有マス)
- atk(攻撃力)
- spd(攻撃速度)
- special_effect_key(特殊効果を識別するキー。ロジックはPHP側の効果クラスで処理)

### 3.2 素材マスタ(materials テーブル想定)
- id
- name
- effect_type(buff_atk / buff_spd / buff_hp 等)
- effect_value
- effect_range(adjacent / global)

### 3.3 合成レシピマスタ(recipes テーブル想定)
- id
- input_items(素材/武器のID配列。JSON形式で保持)
- output_item_id(生成される武器のID)

### 3.4 プレイヤーのバックパック状態(セーブデータ)
- grid_size(width, height)
- placed_items(各アイテムのID・配置座標・向きを持つ配列)
- player_hp

### 3.5 非同期PvP用データ
- 対戦相手のバックパック状態をスナップショットとして保存し、
  戦闘シミュレーションのみをローカル(自分側のPHPロジック)で再生する方式とする
- サーバー同期が必要な範囲を最小化し、個人開発でも運用コストを抑える設計

## 4. 非同期PvPの通信方針(将来フェーズ)

検証計画の段階(疑似検証)ではサーバー通信は不要だが、
実装フェーズを見据えた最小構成を記載する。

- 対戦相手のバックパックデータを取得するための**簡易APIサーバー(PHP/Laravel)**を別途用意
- クライアント(NativePHPアプリ)は起動時・対戦時にAPIへリクエストし、
  対戦相手データをダウンロードしてローカルでシミュレーションを実行
- リアルタイム同期(WebSocket等)は初期フェーズでは採用しない
  (個人開発の運用負荷を抑えるための判断)

## 5. 開発環境・使用技術

| 項目 | 採用技術 |
|---|---|
| 言語 | PHP(Laravel) |
| 第一段階(公開方法) | Webサイトとしてホスティング |
| 第二段階(公開方法) | NativePHPによるデスクトップアプリ化(Windows/Mac/Linux) |
| データベース | Web版: サーバー側DB(MySQL等) / デスクトップ版: ローカルSQLite + 共通APIサーバー |
| 描画 | HTML5 Canvas + JavaScript(薄いレイヤー。Web版・デスクトップ版で共通) |
| バージョン管理 | Git |

## 6. 技術リスク・検討事項

- **Web版とデスクトップ版のコード共有**: 「ロジックはPHP、描画のみJS」の原則を
  崩さないことが、後日のNativePHP移行をスムーズにする鍵になる。
  Web版特有の処理(セッション管理など)をロジック層に混在させないよう注意する
- **NativePHPの成熟度**: 比較的新しいエコシステムのため、デスクトップ化のタイミングで
  パフォーマンスや配布(Steam申請含む)における制約を検証する必要がある
- **保存処理の抽象化**: Web版(サーバーDB)とデスクトップ版(ローカルSQLite)で
  保存先が異なることを見越し、データアクセス層を抽象化しておく
- **戦闘シミュレーションの処理負荷**: 大量アイテム構成時の計算量が問題にならないか、
  検証実装の段階で計測しておく

## 7. 次のステップ

- 検証実装(プロトタイプ)にこの技術構成を適用し、
  「PHPロジック→JS描画」の連携が実用に耐えるかを最優先で確認する
- まずはWebサイトとして公開できる状態を目指して実装を進める
- デスクトップ化(NativePHP導入)は、Web版がある程度動作・検証できた段階で着手する
## 8. 将来検討事項: Nintendo Switch展開について

Web版・デスクトップ版のリリース後、Switchへの展開を検討する場合の前提を記録しておく。

- **現在の技術スタック(PHP/Laravel + NativePHP)のままではSwitchに展開できない**
  - Switch向け開発はUnity・Unreal Engine・Nintendo SDKを使ったネイティブC++が前提であり、
    NativePHPの基盤であるElectron(ブラウザ技術ベースのアプリ)を動かす公式な経路は存在しない
- Switch展開を行う場合は、**Unity等の対応エンジンでゲームロジックを作り直す**ことが実質必須になる
- 参入自体(Nintendo Developer Portalへの登録・NDA・アクセス申請)は個人開発者でも可能だが、
  開発機材(Dev Kit)の購入費用が別途発生する
- オンライン対戦(ランクマッチ・非同期PvP)をSwitchで実現する場合、
  Nintendo独自のオンライン基盤への対応も別途必要になる

**現時点の方針**: Web版・デスクトップ版でゲーム自体を完成させ、反応を見た上で、
需要があればSwitch版は別エンジンでの作り直しとして改めて検討する。
